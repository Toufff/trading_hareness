## 1. 服务变更：SSH 仅接受公钥（2026-09-04 生效）

lightServer 的 sshd 已改为：

```text
PasswordAuthentication no
PermitRootLogin prohibit-password
KbdInteractiveAuthentication no
```

**这不是权限收紧，与信任无关。** 改动前该机器的认证日志里有 971 次密码爆破
失败、0 次成功的密码登录——密码这条路只被公网扫描器使用。

**对你的影响：**

- 用公钥（`~/.ssh/stockpeer_ed25519`）建立隧道的方式**完全不受影响**。
- 改动前已核对每个有登录历史的账号都持有可用公钥，且采用 `reload` 而非
  `restart`，已建立的会话与端口转发全程未中断。
- 如果你有任何脚本、CI 任务或跳板配置靠**密码**连这台机器，它现在会收到
  `Permission denied (publickey)`，请改用密钥。

复现该配置的脚本：`scripts/shared-peer/harden-lightserver-sshd.sh`（幂等，
自带"每个有登录史的账号必须有可用公钥"的防锁死预检）。

## 2. owner 发布期间会发生什么

owner 发布新版本时会重启网关进程并重建反向隧道。这是本文最需要你改代码的
一节。

### 2.1 长连接会失效

重启使你连接池中已建立的连接变成死 socket。`requests.Session` 复用它们时抛
`ConnectionResetError(104, 'Connection reset by peer')`，而 **requests 默认不
重试 POST**，于是发布后你的首批请求会直接失败。

建议只给**连接建立阶段**加重试：

```python
from requests.adapters import HTTPAdapter
from urllib3.util.retry import Retry

session.mount("http://", HTTPAdapter(max_retries=Retry(
    total=2,
    connect=2,        # 只重试连接阶段
    read=0,           # 不重试已发出的请求
    allowed_methods=frozenset(["GET", "POST"]),
    backoff_factor=0.5,
)))
```

不要重试 `read`。本网关全部为只读调用，连接层重试是安全的；读超时重试只会
让耗时与语义变得不确定，没有收益。

### 2.2 发布后的自检

怀疑网关状态时，用 catalog 做探针比用 `/health` 可靠——`/health` 回答的是
网关自身进程的状态，catalog 会真正打到上游：

```bash
curl -sf -H "X-Quant-Read-Key: $QUANT_SHARED_READ_API_KEY" \
  http://127.0.0.1:15682/licensed/stock-api/catalog | head -c 200
```

### 2.3 已发生的中断：2026-09-04 16:48–16:57

一次发布后，连接 owner 数据库与 API 的两条反向隧道断开且**未自动恢复**，直到
人工介入，共 9 分钟。这期间你观察到的现象是：网关 `/health` 仍返回 200，但所
有实际调用返回 500。

根因是 Windows 计划任务的"失败后重启"设置只覆盖任务引擎启动失败，不覆盖动作
自身以非零码退出。**已修复**：改为基于定时触发的守护，实测断连后 63 秒内自动
恢复；当天随后的三次发布均未再出现无人恢复的情况，中断都在秒级。

## 3. 超时预算

批量报价对每只股票发一次上游请求，跨 12 个线程并发，一个满额 300 只的批次约需
**25 秒**上游耗时。

该路径的执行边界原为 30 秒，只剩约 5 秒余量，任何上游抖动都会变成给你的 500。
**2026-09-03 已放宽到 60 秒**，改后连续两次 300 只实测为 24.8 秒与 24.5 秒。

> 请把客户端读超时设在 **90 秒以上**，不要设成 30 秒。

另外，网关**不做任何请求节流**。曾经加过一版每秒令牌桶，因为会让 300 只的批量
撞上执行超时而被移除。`300` 是上游供应商单页的物理上限，不是限速。上游承受能力
是共享的，请自行控制并发，不要把满额批量放进紧循环。

## 4. 数据新鲜度

判断"今天的数据到了没有"，唯一权威字段是 `/health` 里的
`daily_control_plane.trade_date`。它由实际入库行数推导，不会谎报一个并不存在
的日期。

```json
"daily_control_plane": {
  "state": "ready",
  "trade_date": "2026-09-04",
  "daily_rows": 5237,
  "expected_daily_rows": 5253,
  "coverage_ratio": 0.997
}
```

收盘数据由 owner 侧在 **16:00 起**灌入（2026-09-19 起，原 16:40），失败则每 30 分钟重试一次、持续 7 小时。
16:00 之前 `trade_date` 仍是上一交易日属于正常状态，请据此判断，不要在这个窗口
里反复重试。

### 已知数据缺口

**2026-09-02 与 2026-09-03 两个交易日在库中缺失，且不会补回。**

原因是全市场收盘合并要求参考报价的交易日与目标日一致，而参考源是实时报价接口，
事后取不到历史日的报价——补 09-02 只会拿到当前日的报价，交叉覆盖率为 0。另一条
可用的历史日线是前复权数据，被显式禁止进入权威日线表（前复权序列不能充当权威
OHLC）。

日线数据自 2026-09-04 起恢复连续。若你的计算依赖连续交易日序列，请显式处理这两
天的空洞。

## 5. 故障对照

| 状态 | 含义 | 该怎么办 |
| --- | --- | --- |
| `401` | 缺少或不匹配 `X-Quant-Read-Key` | 检查请求头。近期观察到 4 次落在 `/licensed/stock-api/catalog` 上而其余端点正常，大概率是某条调用路径漏带了这个头，建议排查。 |
| `422` | 参数不合法 | 请求体形状或参数值有误，对照 catalog 的 `documented_examples` 修正。 |
| `500` | 网关内部错误 | 常见于 owner 刚发布、你的长连接已失效。先按 §2.1 加连接重试；若持续超过一分钟，隧道可能真的断了，请联系 owner。 |
| `502` | 上游数据源报错 | 供应商侧问题，非鉴权或参数问题，退避后重试。 |
| `503` | 网关被禁用，或上游未配置 | owner 侧配置状态问题，重试无用，请直接联系。 |
| `200` | 成功——但仍需检查 `source_status` | 批量调用可能是 `partial`。**不要只看 HTTP 码就认为数据完整。** |

`source_status.status` 只有在每一页都成功时才是 `completed`，否则为 `partial`。

## 6. 数据库访问守则

除 HTTP 网关外，你的容器栈通过 `db-tunnel` 直连 owner 的 PostgreSQL：

| 项 | 值 |
| --- | --- |
| 数据库 | `trading_hareness` |
| 角色 | `stock_peer` |
| 主 schema | `quant` |
| 链路 | `db-tunnel` 容器 → 反向隧道 → owner 本机 PostgreSQL |

> **这是共享的权威库，不是副本。**
>
> 该角色具备写权限，且这是唯一一份权威数据，没有为 peer 单独复制一份。对
> `quant` schema 下任何表的写入或删除会立即影响 owner 侧的全部计算与报告。
>
> 请按只读使用。确实需要写入时（例如 `market_events`），请事先说明写哪张表、
> 写什么。

### 6.1 批量隧道：批量作业请走 `db-tunnel:5433`

你提出的"批量作业把 SSH 连接占满"是对的，已按此改。原因值得写清楚，因为它决定
了正确用法：

SSH 把每条端口转发当作**同一个 TCP 连接上的 channel**，它们共用同一个拥塞窗口和
同一条排队序列。所以一个 `COPY`／全表导出／回补作业灌满窗口后，盘中查询只能排在
后面等它。本链路实测 RTT **52.5 ms**，这个排队代价不小。在原连接上再加一条
`-R` 是没用的——还是同一个窗口。

因此 owner 侧新开了**一条独立的 SSH 连接**专供批量流量（远端 `15433`，开启
`Compression=yes`），你侧 `db-tunnel` 容器把它暴露为 `5433`：

| 用途 | 地址 | 说明 |
| --- | --- | --- |
| 盘中查询 | `db-tunnel:5432` | 保持原样，不要用它跑批量 |
| 批量／导出／回补 | `db-tunnel:5433` | 独立连接，压缩开启 |

两个端口连的是**同一个库**（owner 本机 55432），只是链路不同，不存在数据差异，
也不需要改连接参数以外的任何东西。验证它确实通到 owner：

```bash
docker compose exec -T db-tunnel sh -c \
  "PGPORT=5433 psql -X -A -t -c 'SELECT 1, inet_server_port()'"
# 期望：1|55432
```

几点必须知道：

- **这是可选能力，默认关闭。** `.env` 里不设 `PEER_BATCH_DB_PORT=5433` 时，容器
  行为与以前完全一致，只有 5432/5681。
- **`db-tunnel` 的健康检查只查 5432 和 5681，不查 5433**，这是故意的：批量通道
  是优化项，把容器健康绑到它上面等于把优化变成故障。
- **owner 侧批量隧道断开时，5433 的连接会单独失败，5432/5681 不受影响。** 看到
  5433 连不上而 5432 正常，说明是 owner 侧批量任务掉了，不是你的问题，请联系
  owner；期间退回 5432 即可，只是会重新开始互相抢带宽。
- 批量作业仍受第 3 节的超时与并发约束，5433 只解决排队互相干扰，不提高上游配额。

## 7. 已知不可用的能力

以下能力依赖当前未配置的付费数据源，会返回明确的 blocked 状态而非静默失败：

- 分钟线 `stk_mins`
- 财报披露日历 `disclosure_date`
- 个股资金流 `moneyflow`

另外，网关端口只绑定 `127.0.0.1`，不对公网开放；从外部机器访问需按
[`SHARED_STOCK_DATA_API.md` §2.2](SHARED_STOCK_DATA_API.md) 自行建立 SSH 转发。
